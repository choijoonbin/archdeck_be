# ArchDeck 제품 기획 기준

기준일: 2026-11-27 · 상태: 제품 기획과 데이터 기반 설계 · 최신 사용자 지시 반영

ArchDeck은 엔지니어가 기술 개념을 이해하고 아키텍처 대안을 비교한 뒤 실무 점검과 개인 기록까지 이어가는 도구다. 첫 콘텐츠는 인증·보안 아키텍처에 집중하되 데이터와 공통 화면 구조를 통해 다른 기술 분야로 확장한다.

## 사용자와 해결할 문제

| 사용자 | 해결할 질문 | 중심 행동 |
|---|---|---|
| 학습하는 엔지니어 | 기술이 왜 필요하고 어떤 순서로 동작하는가 | 구성도와 단계 설명을 함께 보며 학습한다. |
| 설계하는 개발자·기술 리드 | SPA와 BFF처럼 여러 대안 중 어떤 것을 선택해야 하는가 | 동일한 평가 기준으로 비교하고 적용 조건을 확인한다. |
| 호스트 PC의 관리자 | 지식을 어떻게 추가하고 신뢰할 수 있게 유지할 것인가 | 출처·검토일·버전을 가진 콘텐츠를 작성·검증·게시한다. |
| 사내 열람자 | 팀이 공유한 내용을 어떻게 찾아 다시 활용할 것인가 | 로그인해 열람하고 자기 기록을 남긴다. |

핵심 여정은 탐색 → 이해 → 비교·판단 → 점검 → 개인 기록이다. 홈은 이어서 볼 주제와 다음 학습을 안내한다. 학습과 무관한 숫자 카드나 긴 홍보용 첫 화면을 중심으로 만들지 않는다.

## 변경된 결정과 유지하는 요구

| 결정 | 현재 기준 | 근거 |
|---|---|---|
| 로그인 | 아이디·비밀번호 로그인 포함 | 사내 열람을 위해 사용자가 마지막으로 추가한 요구다. 앞선 로그인 제외 결정을 대체한다. |
| 헤더 | 검색·새 지식·전체화면·설정·로그인 상태·로그아웃 | 프로필 중심 계정 기능은 단순화하고 알림은 제외한다. |
| 사용 환경 | 개인 PC에서 관리하고 필요할 때 사내 공유 | 사용자가 확인한 1차 운영 방식이다. |
| 권한 | 관리자 ADMIN, 열람자 READER | 관리자만 콘텐츠·계정을 변경하고 열람자는 게시 콘텐츠를 읽는다. |
| 화면 구조 | DWP형 공통 헤더·내비게이션·본문 | 초기 Linear/Vercel/Raycast 중심의 장식적 방향보다 최신 DWP 구조 요청을 우선한다. |
| 외관 설정 | preset, 좌·우·상단 메뉴, 펼침·축소, 주간·야간·시스템, 밀도·대비·모션·초기화 | 사용자가 명시한 항목과 DWP 외관 설정을 함께 반영한다. |
| 개인 기록 | 브라우저와 로그인 계정별 저장 | 공용 default_user 동기화를 제거하고 계정 전환 시 기록이 섞이지 않도록 한다. 서버 동기화는 후속 범위다. |
| 콘텐츠 원본 | 호스트 PostgreSQL에 게시 콘텐츠 관리 | FE와 BE에 서로 다른 내용을 손으로 중복 작성하는 방식을 해소한다. |

인증은 제품의 접근 기능이다. Keycloak·OIDC·PKCE·BFF는 학습 콘텐츠로 계속 제공하지만, ArchDeck의 로그인에 외부 Keycloak이나 OIDC 인프라를 도입하는 것은 현재 범위가 아니다.

## 벤치마킹을 반영한 제품 구성

- ByteByteGo에서 시각적 설명과 단계별 이해 방식을 참고한다.
- roadmap.sh에서 권장 순서·선행 주제·진도·다음 행동을 참고한다.
- Refactoring.Guru에서 문제·해결·적용 조건·장단점·관련 개념을 일관된 템플릿으로 연결하는 방식을 참고한다.

이는 시장 순위가 아닌 ArchDeck의 제품 적합성 기준이다. 각 서비스의 콘텐츠·그림을 복제하지 않고 독자적인 콘텐츠와 구성도를 만든다. 공식 근거와 후보 비교는 [벤치마킹 문서](01-benchmark.md)에 기록한다.

## 최초 콘텐츠 범위

| 종류 | 출발 범위 | 품질 기준 |
|---|---|---|
| 토픽 | Keycloak IAM, SPA+PKCE, BFF+Token Relay, SPA와 BFF 비교, XSS와 CSRF | 5개 토픽에서 핵심 여정을 완주한다. 흐름이 없는 개념 문서는 정상 표시한다. |
| 비교 | SPA와 BFF, XSS와 CSRF, IAM 솔루션 | 비교 대상과 차원의 의미를 통일하고 장단점을 조건과 함께 설명한다. |
| 용어 | 기존 10개 용어 | 짧은 정의·상세·연관 토픽·출처·검토일을 연결한다. |
| 점검 | 기존 9개 체크포인트를 대조·정비 | 누락된 참조를 보완하거나 정정한다. 단순 체크를 안전성 인증으로 표현하지 않는다. |
| 학습 경로 | 인증·보안 기초를 잇는 첫 안내 경로 | 홈과 상세에서 같은 경로의 다음 주제를 안내한다. 별도 대형 경로 편집기는 후속이다. |

토픽 상세 기본 순서는 문제·전제 → 시스템 구성·신뢰 경계 → 단계·예외 흐름 → 적용·비적용 조건 → 장단점·비교 → 점검 → 관련 개념 → 출처·적용 버전·검토일이다.

## MVP 메뉴와 운영 범위

학습 메뉴는 학습 시작, 아키텍처, 비교, 용어, 체크리스트, 내 서재다. 흐름도는 아키텍처 상세 안에 둔다. 관리자에게는 콘텐츠 스튜디오와 계정 관리를 제공하고 설정은 헤더의 독립 버튼으로 연다.

신규 회원가입, 이메일 인증, 비밀번호 이메일 재설정, SSO, 알림, 댓글·토론, 공개 기여, Git 웹훅, 결제, 팀별 워크스페이스, 계정 간 개인 기록 자동 동기화는 MVP에 넣지 않는다. 비밀번호 초기화는 관리자가 수행한다.

## 사내 공유 구조

목표 구조는 브라우저 → 같은 출처의 웹·API 진입점 → Spring Boot → Docker PostgreSQL이다. 개인·개발 접근과 사내 공유를 구분하고, 사내 공유 전에 인증·권한·세션·CSRF·HTTPS를 검증한다. DB 포트는 호스트의 127.0.0.1에만 연다.

관리자는 계정을 생성하고 열람자는 아이디·비밀번호로 접속한다. 초기·재설정 비밀번호로 로그인한 사용자는 비밀번호 변경 화면으로 이동하며 변경 완료 전에는 콘텐츠에 접근하지 못한다. 인증되지 않은 요청에는 게시 콘텐츠, 검색 결과, 용어 설명도 반환하지 않는다. 관리자 화면을 숨기는 것에 더해 서버가 모든 변경 API의 권한을 검사한다.

공유용 프론트 번들·정적 JSON에는 보호할 본문·초안·검색 메타데이터를 넣지 않는다. 현재 src/data의 샘플을 번들에 포함한 채 API만 보호하는 방식은 로그인 밖에서 콘텐츠를 읽을 수 있으므로 변경해야 한다. 미로그인·세션 만료·연결 실패 시 초기 콘텐츠를 표시하는 fallback은 공유 모드에서 사용하지 않는다. MVP에서 보호 콘텐츠의 오프라인 열람은 제공하지 않는다.

로그인이 추가되었으므로 별도 무인증 읽기 서비스는 두지 않는다. 하나의 서비스에서 ADMIN은 관리하고 READER는 열람하며 서버가 권한을 검사한다. 관리자는 주로 호스트 PC에서 작업하지만 ADMIN의 사내망 접속을 별도 배포로 차단하는 구성은 MVP 필수가 아니다.

MVP 개인 데이터는 계정 ID와 서비스 식별자로 저장 공간을 나눈다. 로그아웃은 세션을 종료하고 현재 화면의 개인 상태와 메모리를 비운다. 같은 계정의 다른 브라우저에는 개인 기록이 자동 복제되지 않으며 JSON 백업·복원으로 이동한다. 공유 PC를 위한 이 기기의 기록 삭제를 제공한다.

## 개발 전 확정해야 할 품질 기준

- 콘텐츠 정확성: 출처, 대상 제품·규격 버전, 검토일, 적용 조건을 보존한다. 보안 관련 단정적 설명과 실행 불가능한 예제를 점검한다.
- 저장 신뢰성: 읽기 초기화가 끝나기 전 자동 쓰기를 시작하지 않는다. 저장 완료·이 기기에 저장·실패를 구분한다.
- 일관성: 서버의 빈 목록은 정상 응답으로 다루며 과거 샘플을 자동 부활시키지 않는다. 마지막 정상 캐시와 초기 샘플의 출처를 구분한다.
- 접근성: 키보드, 보이는 초점, 모달 초점 관리, 색 외의 상태 표현, 고대비, 모션 축소를 지원한다.
- 반응형: 1440·1280·390·320px과 200% 확대에서 탐색·설정·로그인·학습 흐름을 확인한다.
- 변경 관리: 콘텐츠 수정 시 revision 충돌을 검출하고, 검토·게시 기준을 통과한 콘텐츠만 공유한다.
- 데이터 보존: 기존 H2와 브라우저 기록을 백업한 뒤 별도 PostgreSQL로 변환·대조한다. 이번 설계만으로 기존 앱을 새 DB에 연결하지 않는다.
- 관측·복구: 로그인 실패·서버 오류·저장 실패를 추적하되 비밀번호·세션·개인 메모는 로그에 남기지 않는다. DB 백업과 복원 절차를 검증한다.

## 이번 산출물과 실제 구현의 경계

이번 작업은 제품 기준, 벤치마킹, 메뉴·설정·인증 설계, PostgreSQL DDL, Docker 실행 기반과 검증 결과를 만든다. 기존 FE와 Spring 앱의 인증·레이아웃·DB 전환은 [작업 계획](05-implementation-plan.md)의 후속 구현 항목이다. 현재 앱을 새로 설계한 사내 서비스가 완료된 것으로 취급하지 않는다.

최신 문서 간 충돌이 있으면 이 문서의 최종 사용자 요구를 우선하고 같은 작업에서 관련 문서를 정정한다.
