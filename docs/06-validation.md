# ArchDeck 기획과 데이터 기반 검증 결과

검증일: 2026-11-27 · 대상: 전문가 검토 문서와 새 PostgreSQL Docker 기반

기획·UX·데이터·인증 설계를 통합했고 새 DB를 실제 실행해 테이블과 복구 기반을 확인했다. 앱의 로그인, DWP형 레이아웃, 기존 H2 이관은 아직 구현 대기다.

## 전문가 검토와 반영한 결론

| 검토 영역 | 반영한 결론 |
|---|---|
| 제품·글로벌 벤치마킹 | ByteByteGo·roadmap.sh·Refactoring.Guru를 제품 적합성 기준 3선으로 선정. 공식 기능과 ArchDeck의 적용 제안을 구분 |
| UX·프론트 구조 | 6개 학습 메뉴와 관리자 도구, 상세 URL, 흐름 없는 문서, DWP형 메뉴·설정, 로그인·초기 비밀번호 변경 여정 |
| 데이터·DevOps | 공통 콘텐츠·관계·출처·이력, 같은 토픽 안의 그래프 FK, 학습 경로, 계정·JDBC 세션의 18개 테이블 |
| 인증·공유 | 단순 아이디·비밀번호, ADMIN·READER, Argon2id, 서버 세션·CSRF, 같은 출처의 HTTPS 공유 |
| 교차 검토 | 이전 무로그인·서비스 분리 정책 정정, 보호 콘텐츠 번들 제거, serviceId+user UUID 저장 키, 안정적인 legacy ID 이관, 학습 백업과 DB 백업 구분 |

## SQL 무결성 검사

[db/verify.sql](../db/verify.sql)은 임시 fixture와 성공·실패 검사를 한 트랜잭션에서 실행한 뒤 전부 rollback한다. 아래 9개 그룹이 원본 DB와 복원 검증 DB 양쪽에서 통과했다.

| 검사 그룹 | 확인한 동작 |
|---|---|
| 스키마 존재 | 18개 기본 테이블 |
| 계정 제약 | 인코더 표시 없는 비밀번호 문자열, 잘못된 역할, 중복 아이디 거부 |
| 콘텐츠 제약 | 중복 slug, 배열 payload, 중복 메타데이터, 검토일 없는 게시 거부 |
| 그래프 FK | 다른 토픽의 노드 참조, 토픽 외 그래프 소유, 없는 단계 연결 거부 |
| 학습 경로 | 토픽 외 항목과 중복 순서 거부 |
| 관계·이력·삭제 | 출처 연결, revision 작성자, 참조된 토픽·작성자 삭제 제한 |
| 낙관 잠금 SQL | 일치하는 버전 갱신 1건, 오래된 버전 갱신 0건 |
| 한글 통합 검색 | 공백 정규화와 부분 검색, 본문·노드·연결선·단계·태그 검색 |
| JDBC 세션 구조 | 세션 저장과 삭제 시 속성 cascade |

계정 검사에서 쓰는 인코더 문자열은 로그인 가능한 실제 비밀번호 해시가 아닌 스키마 fixture다. 이는 Argon2 암호 연산 검증이나 로그인 통합 테스트가 아니다. 애플리케이션의 스키마별 payload 검증·역할 검사·revision 저장은 후속 구현에서 별도로 시험한다.

## 재시작과 백업·복원

1. db 컨테이너를 재시작한 뒤 healthy 상태와 18개 테이블·분류·태그 보존을 확인했다.
2. pg_dump custom 형식으로 schema와 데이터를 백업했다. 소유권·권한 의존성을 제외하고 세션 두 테이블의 데이터도 제외했다.
3. 같은 프로젝트의 PostgreSQL에 무작위 이름의 별도 검증 DB를 만들고 pg_restore를 수행했다.
4. 원본·복원의 테이블 수, 콘텐츠·계정·세션 수와 분류·태그의 값·정렬 결과가 같은지 대조했다.
5. 복원 DB에서 9개 SQL 검사 그룹을 다시 실행해 통과했다.
6. 이 작업에서 만든 임시 복원 DB만 삭제했다. 본 DB·컨테이너·볼륨은 유지했다.

이번 백업 파일은 Git에서 제외된 db/backups 아래에 권한 0600으로 보존한다. 현재는 계정·콘텐츠가 없는 초기 기준 백업이다. 실계정 운영 후의 DB 백업에는 해시 등 민감 데이터가 포함될 수 있으므로 학습 JSON 백업과 구분한다. 실제 복구 때는 세션 제거·auth_version 증가·재로그인 절차를 적용한다.

## 이번 검증이 포함하지 않는 것

- 실제 로그인·비밀번호 암호 연산·CSRF·역할·세션 만료·HTTPS는 아직 앱에 연결되지 않았다.
- 기존 H2 데이터와 브라우저 기록을 새 UUID·콘텐츠 스키마로 이관하지 않았다.
- 프론트 화면·테마·메뉴 배치를 수정하지 않았으므로 새 UX의 시각 검증도 아직 수행하지 않았다.
- 기존 API의 빈 흐름 오류·공용 default_user·저장 실패 표시 등은 작업 목록에 남아 있다.
- 여러 사내 단말의 접속, 회사 인증서 신뢰, 성능·로그인 동시 부하는 앱 통합 후 확인한다.

기존 분석 때 프론트 빌드와 Maven 검사는 통과했으나 앱 자동 테스트는 없었다. 서버 데이터 기반 읽기 전용 렌더링에서는 SPA vs BFF와 XSS vs CSRF의 빈 flowSteps 오류를 재현했다. 현재 DB 기반의 성공을 기존 앱 오류 해결로 표현하지 않는다.
